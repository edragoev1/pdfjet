PDFjet vs Apache PDFBox
=======================

PDFjet 9.0.0 (master) compared with Apache PDFBox 3.0.8, the current PDFBox
release (July 2026; PDFBox 4.0 is not released). Written 2026-09-13; the sizes and counts were updated 2026-09-14 for
master at 67bcbb69.
Benchmarks were run on one machine: AMD Ryzen 5 5600G (12 threads), Linux,
OpenJDK 21.0.12.1.


1. Summary
----------

PDFBox is a toolbox for PDF files that already exist: it extracts text,
renders pages to images, prints, splits and merges, fills forms, signs, and
validates PDF/A-1b. For creating documents it offers a low-level drawing API.

PDFjet is a document generator: tables, text blocks, charts, barcodes, SVG,
accessible (PDF/UA) and archival (PDF/A) output, in four languages with the
same API and the same output. It is a tenth of PDFBox's size and has no
dependencies. Writing the same 500-page multilingual document with an
embedded font, PDFjet took 72 ms in Java and PDFBox 21,269 ms.

The strongest positioning is not "a smaller PDFBox" but "the document
generator for teams that ship in Java, C#, Go and Swift", with PDFBox left to
the jobs of editing existing files.


2. Top 10 advantages
--------------------

Strongest first; each is backed by the benchmarks in section 5 or by the
source.

 1. Accessible and archival PDFs are one setting.
    PDF/UA-1 and PDF/A-1a, 1b, 2a, 2b, 3a and 3b are built in, and the
    examples pass veraPDF in CI. PDFBox leaves tagging and PDF/A structure to
    the developer.

 2. One API in four languages, with the same output.
    Java, C#, Go and Swift produce matching PDFs, and CI compares every
    port's examples with Java's. PDFBox is Java only.

 3. Very fast with real embedded fonts.
    A 500-page Latin, Greek and Cyrillic document in 72 ms in Java, against
    21,269 ms in PDFBox, and a first document in a new JVM in 94 ms against
    1,379 ms. PDFBox's time comes from the
    Devanagari substitution rules it applies for Noto Sans; a font without
    those tables would narrow the gap.

 4. Low memory, even for long documents.
    When a new page starts, PDFjet compresses the previous page's content,
    writes it out and frees its buffer; PDFBox keeps the whole document until
    it saves. The 500-page document allocated 35 to 38 MB in Java against
    38,404 MB in PDFBox. Allocations were measured, not peak memory.

 5. No dependencies and a small footprint.
    One 0.39 MB jar, against PDFBox's 3.84 MB of jars plus commons-logging, and
    Bouncy Castle for signing.

 6. Page layout is built in.
    Tables that break across pages and repeat their header rows, wrapped text
    blocks, columns, XY, bar and donut charts, and calendars. With PDFBox these need third-party
    libraries or code of one's own.

 7. Barcodes are built in.
    EAN-13, UPC-A, Code 39, Code 128, QR, Data Matrix and PDF417, drawn as
    vectors.

 8. Fonts are ready to use.
    272 bundled fonts, each compressed once ahead of time, so a document
    spends no time on its fonts, including CFF-based OpenType families such
    as IBM Plex that PDFBox 3.0.8 cannot embed.

 9. SVG images become vector graphics.
    Paths, curves and elliptical arcs are drawn as PDF paths. PDFBox has no
    SVG support.

10. Hardened and tested.
    Limits on decoded sizes and image headers guard against malicious input,
    unit tests run in all four ports, and CI checks the PDF output across the
    ports and with veraPDF.

Claims to avoid:
- Smaller files: PDFBox's files are smaller for short documents, because it
  subsets fonts and writes object streams.
- Editing existing PDFs: PDFBox extracts text, renders, fills forms, signs,
  splits and merges; PDFjet does none of these.
- The license or right to left text as selling points: both licenses are
  permissive, and Arabic and Hebrew are not the main market.
- Easier to install: PDFBox is one line on Maven Central; PDFjet is not
  published to Maven Central or NuGet yet.

5. Benchmarks
-------------

Configurations:

  PDFjet, IBM Plex Sans      IBMPlexSans-Regular.otf.stream (45,868 bytes;
                             the .otf is 136,352 bytes), in Java
  PDFjet, Noto Sans          NotoSans-Regular.ttf.stream (291,446 bytes;
                             the .ttf is 629,024 bytes), in Java
  PDFBox, Noto Sans subset   NotoSans-Regular.ttf, PDType0Font.load with
                             embedSubset true (the default)
  PDFBox, Noto Sans full     NotoSans-Regular.ttf, embedSubset false

PDFBox 3.0.8 cannot embed IBM Plex Sans: loading IBMPlexSans-Regular.otf
fails with "True Type fonts using CFF outlines are not supported". Noto Sans
is a TrueType font with the same scripts, which both libraries can embed.

Method: every page has 60 lines of 10 point text, a line each of
"The quick brown fox jumps over the lazy dog",
"Ξεσκεπάζω την ψυχοφθόρα βδελυγμία" and
"Съешь же ещё этих мягких французских булок", drawn with one call per line:
Page.drawString in PDFjet, beginText/showText/endText on a
PDPageContentStream in PDFBox. Each configuration and size ran in its own JVM
(-Xmx4g) with 2 warm-up runs and 7 measured runs, or 3 measured runs when a
run took more than 5,000 ms; the median is reported. Documents were written
to memory. Allocations are the bytes the thread allocated per document. All
figures are from one session. Section 10 compares the four ports of PDFjet
with each other.

  PDFjet Java, Noto Sans        73 ms       848,576 bytes   38 MB

  PDFBox, Noto Sans full        20,883 ms   728,346 bytes   38,383 MB

  PDFBox, Noto Sans full        352,314    393,898     477,297     728,346

PDFjet is about 290 times faster at 500 pages, with about a thousandth of the
allocations. PDFBox's time grows with the number of text calls: about 0.7 ms
and 1.3 MB allocated for each line of text. Stack samples of the PDFBox
thread show where: PDAbstractContentStream.applyGSUBRules runs fontbox's
GsubWorkerForDevanagari, which compiles regular expressions
(GlyphArraySplitterRegexImpl, CompoundCharacterTokenizer) for every showText
call, because Noto Sans has Devanagari substitution tables. The speed of
PDFBox with an embedded font therefore depends on the tables in the font;
with Noto Sans, the widely used free font for Latin, Greek and Cyrillic, it
takes this path whether or not it subsets.

5.4 File size and fonts

A 3-page sample of each configuration:

                              file           embedded font program
  PDFjet Java, IBM Plex Sans  65,231 bytes   42,564 bytes, whole font
  PDFjet Java, Noto Sans      347,906 bytes  281,523 bytes, whole font
  PDFBox, Noto Sans subset    11,303 bytes   6,655 bytes, subset
  PDFBox, Noto Sans full      313,186 bytes  296,405 bytes, whole font

PDFjet does not subset fonts, by design. Its fonts are compressed once, ahead
of time, with the best compression available (Zopfli, in
GenerateStreamFontsFiles), into the .stream files, and a document embeds them
as they are, so generating a document spends no time on its fonts. The whole
Noto Sans font PDFjet embeds is 5% smaller than the one PDFBox compresses at
each save (281,523 against 296,405 bytes), and IBM Plex Sans, a CFF font that
PDFBox cannot embed, is a seventh of that. A subset gives smaller files for
short documents; with IBM Plex Sans, PDFjet's 500-page file is within 35% of
PDFBox's subset file.

Past the font, each page adds about 1,020 bytes to a PDFjet file and about 840
bytes to a PDFBox file, and PDFBox compresses its objects into object streams
with a cross-reference stream, which PDFjet does not write. That is why the
PDFBox file with the whole font is smaller than PDFjet's with Noto Sans.

5.5 Correctness
MuPDF extracts all three sample lines, in Latin, Greek and Cyrillic, from the
files of all four configurations.


6. Where PDFBox is ahead
------------------------

- Everything about existing files: text extraction, rendering, printing,
  splitting and merging, form filling, signatures and PDF/A validation.
- Smaller files for short documents, as it subsets fonts at each save, and
  smaller pages, with object streams. PDFjet trades the subset for no font
  work per document (see 5.4).
- Distribution and trust: Maven Central, the Apache brand, a long history
  and a large user community.


7. How to differentiate PDFjet
------------------------------

Position PDFjet as the document generator and PDFBox as the PDF toolbox. The
two are complementary; competing on PDFBox's ground means years of work on
features its users already have.

1. One API in four languages, with the same output.
   Java, C#, Go and Swift, with the examples of every port compared with
   Java's in CI, pixel by pixel and operator by operator. PDFBox is Java only.
   Target teams with a Java or .NET back end, Go services and iOS or macOS
   apps, who today use a different PDF library on each platform.

2. The layout work is done.
   Tables that break across pages and repeat their headers, text blocks,
   charts, barcodes including QR, Data Matrix and PDF417, and SVG. With PDFBox
   these need third-party libraries or code of one's own. Lead with invoices,
   statements, reports, shipping labels, tickets and certificates, and show
   the lines of code each one takes.

3. Accessible and archival documents without a specialist.
   PDF/UA-1 and PDF/A-1, 2 and 3 are one setting, and the examples pass
   veraPDF in CI. PDFBox leaves tagging and PDF/A structure to the developer.
   The European Accessibility Act, in force since June 2025, and Section 508
   make this a buying reason for public sector, banking, insurance and
   utilities.

4. Fast with real fonts, at any volume.
   A 500-page Latin, Greek and Cyrillic document in 72 ms in Java against
   21,269 ms, with 35 to 38 MB of allocations against 38,404 MB, and a first
   document in a new JVM in 94 ms against 1,379 ms.
   That is the difference between generating statements
   on request and queueing them, and it fits serverless functions, where cold
   starts are paid on every scale-up.

5. Fonts that work, prepared once.
   272 bundled fonts compressed once with the best compression available, so
   a document spends no time on its fonts, including CFF-outline families
   such as IBM Plex that PDFBox 3.0.8 cannot embed. Publish the benchmark with
   its method, including the file sizes where PDFBox's subsets are smaller.

6. Small and dependency-free.
   A 0.39 MB jar with no dependencies, against 3.84 MB and commons-logging.

7. Built to be run on untrusted input.
   Limits on decoded sizes and image headers, and unit tests in all four
   ports, are material for security reviews in regulated industries.


8. Gaps to close
----------------

In order of what they unlock:

1. Distribution. Publish to Maven Central and NuGet, list the Swift package
   on the Swift Package Index, and ship the fonts inside the packages (the
   font constants are paths relative to the working directory today).
   Developers compare libraries by what they can add in one line.
2. Object streams and a cross-reference stream (PDF 1.5), as an option: each
   PDFjet page is about 20% larger than a PDFBox page. Font subsetting stays
   out by design.
3. Form fields and digital signatures, as the enterprise features that most
   often send a team to PDFBox. Java, .NET and Go have the cryptography in
   their standard libraries, so this can stay dependency-free there.
4. Merge, split and page import, on top of the PDF reader that exists.
5. Text extraction, at least plain text, for search indexing and tests.

Not worth leading with: the license (MIT and Apache 2.0 are both permissive)
and right to left text, as Arabic and Hebrew are not the main market.


9. Caveats
----------

- One machine and one JDK; absolute times will differ elsewhere, and PDFBox
  4.0 may change the results.
- PDFBox's slow path comes from the Devanagari substitution tables in Noto
  Sans; with a TrueType font without them PDFBox may be much faster. PDFBox
  could not be measured with IBM Plex Sans, which it cannot embed.
- The benchmark draws one line per call; code that draws a whole paragraph
  per call would make fewer calls in either library.
- The benchmark programs are not in the repository.

10. The four ports of PDFjet
----------------------------

The document of section 5, with IBM Plex Sans (.otf.stream) and 60 lines of
Latin, Greek and Cyrillic text per page, written by each port of PDFjet in one
session, with 2 warm-up runs and 7 measured runs; the median is reported.
Java: OpenJDK 21.0.12.1. C#: .NET 8.0.424, Release build. Go: Go 1.27.1.
Swift: Swift 6.3.3, release build.

  Port    100 pages   500 pages   file size,      peak memory,
                                  500 pages       500 pages
  Java    15 ms       73 ms       571,768 bytes   96 MB
  C#      22 ms       70 ms       571,768 bytes   57 MB
  Go      10 ms       51 ms       521,916 bytes   10 MB
  Swift   22 ms       94 ms       718,115 bytes   29 MB

Peak memory is the largest resident size, from /usr/bin/time, of a process
that writes one 500-page document, with each runtime at its defaults. It
includes the runtime itself, so the JVM and the .NET runtime start higher
than Go and Swift before the first page is drawn.

Java and C# write files of the same size; at 500 pages Go's are about 9%
smaller and Swift's about 26% larger. MuPDF extracts the three lines from the
3-page samples of every port.
