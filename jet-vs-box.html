1Summary

PDFBox is a toolbox for PDF files that already exist: it extracts text, renders pages to images, prints, splits and merges, fills forms, signs, and validates PDF/A-1b. For creating documents it offers a low-level drawing API.

PDFjet is a document generator: tables, text blocks, charts, barcodes, SVG, accessible (PDF/UA) and archival (PDF/A) output, in four languages with the same API and the same output. It also merges existing PDFs and splits them into parts, is a tenth of PDFBox’s size and has no dependencies. Writing the same 500-page multilingual document with an embedded font, PDFjet took 72 ms in Java and PDFBox 21,021 ms.

iText Core 9.7.1, the open source edition of iText, is as fast on long documents (71 ms) but slower on shorter ones, and it needs twice the allocations, about 1.5 times the peak memory, 2.4 times the start-up time and 15 times the jars, dependencies included.

On Example_43’s 2,546-page table, PDFjet’s BigTable took 2.0 s, iText 2.0 s drawing the table with PdfCanvas and 35 s with its own Table, and PDFBox 12.5 s. Drawn with the same calls as on PdfCanvas, on its Page, PDFjet took 2.2 s and allocated 32% more than iText. With every page kept for the footers, PDFBox finished in the smallest heap, 128 against 256 MB; written page by page, PDFjet and iText both finished in 32 MB.

2Top 10 advantages

Strongest first; each is backed by the benchmarks in section 5 or by the source.

  1. Accessible and archival PDFs are one setting.

    PDF/UA-1 and PDF/A-1a, 1b, 2a, 2b, 3a and 3b are built in, and the examples pass veraPDF in CI. PDFBox leaves tagging and PDF/A structure to the developer.

  2. One API in four languages, with the same output.

    Java, C#, Go and Swift produce matching PDFs, and CI compares every port’s examples with Java’s. PDFBox is Java only.

  3. Very fast with real embedded fonts.

    A 500-page Latin, Greek and Cyrillic document in 72 ms in Java, against 71 ms in iText and 21,021 ms in PDFBox, and a first document in a new JVM in 93 ms, against 226 ms and 1,293 ms. iText is as fast on long documents but not on shorter ones: 26 against 17 ms at 100 pages. PDFBox’s time comes from the Devanagari substitution rules it applies for Noto Sans; a font without those tables would narrow the gap. On Example_43’s 2,546-page table in IBM Plex Sans, PDFjet’s BigTable took 2.0 s, level with iText drawing it on PdfCanvas, PDFBox 12.5 s and iText’s Table 35 s.

  4. Low memory, even for long documents.

    When a new page starts, PDFjet compresses the previous page’s content, writes it out and frees its buffer; PDFBox keeps the whole document until it saves. The 500-page document allocated 36 to 39 MB in Java, against 71 to 81 MB in iText and 38,241 to 38,262 MB in PDFBox, and the whole JVM process peaked at 90 to 95 MB, against 132 to 137 MB and 383 to 384 MB. iText also keeps its pages until the document is closed; flushing each page brought it to 125 to 133 MB. A BigTable that keeps its pages for “Page i of N” footers is the exception: it needed a 256 MB heap for Example_43, where the same table written page by page finished in 32 MB (see 5.6).

  5. No dependencies and a small footprint.

    One 0.39 MB jar, against PDFBox’s 3.85 MB of jars with commons-logging, and Bouncy Castle for signing, and iText’s 5.75 MB: 3.29 MB of its own jars and 2.47 MB of Jackson, SLF4J and a Bouncy Castle connector.

  6. Page layout is built in.

    Tables that break across pages and repeat their header rows, wrapped text blocks, columns, XY, bar and donut charts, and calendars. With PDFBox these need third-party libraries or code of one’s own.

  7. Barcodes are built in.

    EAN-13, UPC-A, Code 39, Code 128, QR, Data Matrix and PDF417, drawn as vectors.

  8. Fonts are ready to use.

    272 bundled fonts, each compressed once ahead of time, so a document spends no time on its fonts, including CFF-based OpenType families such as IBM Plex that PDFBox 3.0.8 cannot embed.

  9. SVG images become vector graphics.

    Paths, curves and elliptical arcs are drawn as PDF paths. PDFBox has no SVG support.

  10. Hardened and tested.

    Limits on decoded sizes and image headers guard against malicious input, unit tests run in all four ports, and CI checks the PDF output across the ports and with veraPDF.

PDFjet does not subset fonts, by design. Its fonts are compressed once, ahead of time, with the best compression available (Zopfli, in GenerateStreamFontsFiles), into the .stream files, and a document embeds them as they are, so generating a document spends no time on its fonts. The whole Noto Sans font PDFjet embeds is 5% smaller than the one PDFBox compresses at each save (281,523 against 296,405 bytes), and IBM Plex Sans, a CFF font that PDFBox cannot embed, is a seventh of that. iText embeds the whole Noto Sans at the same 296,405 bytes as PDFBox, and the whole IBM Plex Sans at 44,292 bytes, 4% more than PDFjet. A subset gives smaller files for short documents; with IBM Plex Sans, PDFjet’s 500-page file is within 35% of PDFBox’s subset file and 14% larger than iText’s.

Past the font, each page adds about 1,020 bytes to a PDFjet file, about 960 bytes to an iText file and about 840 bytes to a PDFBox file, and PDFBox compresses its objects into object streams with a cross-reference stream, which PDFjet does not write, nor iText at its defaults. That is why the PDFBox file with the whole font is smaller than PDFjet’s with Noto Sans.

5.6 A 2,546-page table: Example_43

Example_43 draws data/Electric_Vehicle_Population_Data.csv, 124,716 rows and 29.7 MB, as a BigTable: 9 of the 17 columns, with widths measured from every field, shaded alternate rows, a line above each row, vertical lines, the header on every page and a “Page i of N” footer, on 2,546 Letter landscape pages in IBM Plex Sans SemiBold and Regular. PDFjet, iText and PDFBox also draw the same table through one driver that follows BigTable step by step: the same two passes over the file, the same geometry and the same operators, on PDFjet’s Page, PdfCanvas and PDPageContentStream. iText also ran with its own Table in large-table mode, the API an iText user would reach for: added to the Document before its rows, flushed every 50 rows, with header cells, and with immediate flushing off so that the footers can be added before the document is closed, as iText documents for “Page X of Y”. PDFBox has no table API. These five configurations keep every page until the footers are drawn at the end. Two more take the number of pages from the first pass and draw each footer with its page, so that each page is written when the next one starts: PDFjet’s pages are added to the PDF as they are created, and iText flushes the previous page.

PDFBox used the TrueType build of IBM Plex Sans from IBM’s repository, as it cannot embed the OpenType fonts that PDFjet and iText use. All seven files have 2,546 pages and end with “Page 2546 of 2546”, and their first pages render alike; the pages drawn on PDFjet’s Page render the same as BigTable’s, pixel for pixel. The PDFjet and PdfCanvas rows were measured in one session at 6c15ef9e, whose library is that of 5c0ca7e1; the iText Table and PDFBox rows are from an earlier session the same day, in which BigTable took 1,945 ms and PdfCanvas 2,030 ms.

PDFjet’s BigTable and iText’s PdfCanvas are level, 2,011 against 2,025 ms, 6.2 times faster than PDFBox and 18 times faster than iText’s Table, which also allocates 36 times as much as BigTable, needs an 8 GB heap and writes a file 75% larger.

Drawn with the same calls, PDFjet is behind iText: on Page the table took 7% longer than on PdfCanvas, 2,165 against 2,025 ms, and allocated 32% more, 1,460 against 1,109 MB; page by page, 3% longer and 29% more. BigTable takes 7% less time than the same drawing on Page, as it writes only a position for each string, where Page.drawString writes a text matrix and the text color, and copies the color.

Memory depends on whether the pages are kept. BigTable keeps every page until the footers are drawn, and a page that has not been added to the PDF holds its content uncompressed: 97.5 MB for the 2,546 pages, 38,307 bytes a page, against 11.6 MB compressed. PDFBox compresses each page’s content as the page is closed, so with every page kept it finished in a 128 MB heap against 256 MB for PDFjet and iText, and peaked at 459 against 809 to 861 MB. Written page by page, PDFjet and iText finished in a 32 MB heap and peaked at 391 and 404 MB with the JVM at its defaults; PDFBox writes a document only when it is saved.

6Where PDFBox is ahead

  • Most of the work on existing files: text extraction, rendering, printing, form filling, signatures, PDF/A validation, merging and splitting that keep the tagging, and a merge that also keeps bookmarks, form fields, page labels and named destinations (see the Merge and Split rows in section 4).
  • Smaller files for short documents, as it subsets fonts at each save, and smaller pages, with object streams. PDFjet trades the subset for no font work per document (see 5.4).
  • Memory for a document whose pages are all kept until it is complete: on Example_43’s 2,546 pages PDFBox finished in a 128 MB heap and peaked at 459 MB, against 256 and 861 MB for BigTable, as it compresses each page when the page is closed. Written page by page, PDFjet finished in 32 MB (see 5.6).
  • Distribution and trust: Maven Central, the Apache brand, a long history and a large user community.

7How to differentiate PDFjet

Position PDFjet as the document generator and PDFBox as the PDF toolbox. The two are complementary; competing on PDFBox’s ground means years of work on features its users already have.

  1. One API in four languages, with the same output. Java, C#, Go and Swift, with the examples of every port compared with Java’s in CI, pixel by pixel and operator by operator. PDFBox is Java only. Target teams with a Java or .NET back end, Go services and iOS or macOS apps, who today use a different PDF library on each platform.
  2. The layout work is done. Tables that break across pages and repeat their headers, text blocks, charts, barcodes including QR, Data Matrix and PDF417, and SVG. With PDFBox these need third-party libraries or code of one’s own. Lead with invoices, statements, reports, shipping labels, tickets and certificates, and show the lines of code each one takes.
  3. Accessible and archival documents without a specialist. PDF/UA-1 and PDF/A-1, 2 and 3 are one setting, and the examples pass veraPDF in CI. PDFBox leaves tagging and PDF/A structure to the developer. The European Accessibility Act, in force since June 2025, and Section 508 make this a buying reason for public sector, banking, insurance and utilities.
  4. Fast with real fonts, at any volume. A 500-page Latin, Greek and Cyrillic document in 72 ms in Java against 21,021 ms, with 36 to 39 MB of allocations against 38,262 MB, and a first document in a new JVM in 93 ms against 1,293 ms. Against iText, which is as fast on long documents, lead with memory and start-up: a 90 MB peak against 132 MB, half the allocations, 93 against 226 ms for a first document, and one 0.39 MB jar against 5.75 MB. On a 2,546-page table, PDFjet took 2.0 s, PDFBox 12.5 s and iText’s own Table 35 s. That is the difference between generating statements on request and queueing them, and it fits serverless functions, where cold starts are paid on every scale-up.
  5. Fonts that work, prepared once. 272 bundled fonts compressed once with the best compression available, so a document spends no time on its fonts, including CFF-outline families such as IBM Plex that PDFBox 3.0.8 cannot embed. Publish the benchmark with its method, including the file sizes where PDFBox’s subsets are smaller.
  6. Small and dependency-free. A 0.39 MB jar with no dependencies, against 3.85 MB with commons-logging for PDFBox and 5.75 MB with Jackson and SLF4J for iText.
  7. Built to be run on untrusted input. Limits on decoded sizes and image headers, and unit tests in all four ports, are material for security reviews in regulated industries.

8Gaps to close

In order of what they unlock.

  1. Distribution. Publish to Maven Central and NuGet, list the Swift package on the Swift Package Index, and ship the fonts inside the packages (the font constants are paths relative to the working directory today). Developers compare libraries by what they can add in one line.
  2. Compress the content of a detached page when it is finished. A BigTable keeps all its pages until the “Page i of N” footers are drawn, each with its content uncompressed: 97.5 MB for Example_43’s 2,546 pages, against the 11.6 MB they take compressed. That is why PDFBox finished the table in half the heap; written page by page, the same table finished in 32 MB (see 5.6).
  3. Make Page.drawString as lean as iText’s showText. Drawn with the same calls, Example_43’s table took 2,165 ms on Page and allocated 1,460 MB, against 2,025 ms and 1,109 MB on PdfCanvas. For each string it writes a text matrix and the text color and makes two arrays for the color, where BigTable writes only a position and took 2,011 ms (see 5.6).
  4. Object streams and a cross-reference stream (PDF 1.5), as an option. Each PDFjet page is about 20% larger than a PDFBox page. Font subsetting stays out by design.
  5. Form fields and digital signatures, as the enterprise features that most often send a team to PDFBox. Java, .NET and Go have the cryptography in their standard libraries, so this can stay dependency-free there.
  6. Tagging, bookmarks and form fields in merged and split documents. Merge and split ship in 9.0.0 and keep each page with its annotations and links; the tagging, bookmarks and form fields of the documents are left out. Tagging comes first: without it a merged or split PDF/UA document is no longer accessible, and PDFBox keeps it in both.
  7. Text extraction, at least plain text, for search indexing and tests.

Not worth leading with: the license (MIT and Apache 2.0 are both permissive) and right to left text, as Arabic and Hebrew are not the main market.

9Caveats

  • One machine and one JDK; absolute times will differ elsewhere.
  • PDFBox could not be measured with IBM Plex Sans, which it cannot embed.
  • iText was measured through its low-level PdfCanvas, the counterpart of the PDFBox and PDFjet calls; its layout API (Document, Paragraph) was not measured.
  • Peak memory includes the JVM, which every configuration pays alike.
  • The smallest heap in 5.6 was found in steps of a factor of two.
  • The benchmark draws one line per call; code that draws a whole paragraph per call would make fewer calls in either library.
  • The benchmark programs are in benchmarks/: benchmarks/run.sh builds and runs them, and benchmarks/README.md describes the method and lists the results. Section 10 was measured with each port’s own build.
