Second audit, for the v9.0.0 release

PDFjet API Cleanup

The eighteen suggestions of the first audit are done or parked for 10.0. This second pass read the four ports class by class for code drift, for what is still public by accident, and for names that say the wrong thing. It found three bugs and two dozen places where one port does something the others do not; the bugs and the drift that could crash or misplace something were fixed the same day and are listed at the end. What remains is drift in error handling and signatures, and a dozen names worth changing before the release.

Basis: audit-api.py --dump at 533ecc67 (102 lines, 101 public types per port), a method-by-method reading of Page, PDF, the shapes, the text classes, the charts and the annotations in all four ports, and the 50 examples. 14 September 2026

Drift between the ports

Places where a port behaves differently from the other three, in output or in how it fails. None changes the 50 examples, which is why the check does not catch them.

Empty strings are written by three ports and skipped by Go 9.0.0

Finding

PDF.setTitle("") and the other metadata setters write /Title <FEFF> and an empty XMP element in Java, C# and Swift; Go, which cannot tell unset from empty, writes nothing. The annotation writer does the same with an empty title or contents: /T <> in three ports, nothing in Go, while the FileAttachment branch already skips empties everywhere.

Suggestion

Skip empty strings in the nullable ports too. An empty Info entry or annotation title serves no one.

Go and Swift stop the program where the others throw 9.0.0

Finding

The port rule is that Go returns an error where a function returns one and Swift throws PDFjetError. Page.drawPath and drawPoint panic in Go and call fatalError in Swift; Page.setTextRenderingMode panics in Go; Go PDF.AddObjects panics when the PDF has no /Pages, Complete panics when the stream cannot be flushed, and NewPDFFile panics when the file cannot be created, while Read in the same file returns an error.

Suggestion

DrawPath, DrawPoint, AddObjects and Complete return error, NewPDFFile returns (*PDF, error); Swift drawPath and drawPoint throw.

Go has no reader-only PDF, and a file constructor the others lack 9.0.0

Finding

Java, C# and Swift have a PDF() constructor for reading an existing document. Go has only NewPDF(writer), which writes the header at once, so the Go examples open an output file just to call Read. Go alone has NewPDFFile(path), which opens and closes the file.

Suggestion

Add a Go constructor for reading, and either add PDF(path) to the other ports or list NewPDFFile under the documented Go conveniences.

Warnings go to different places 9.0.0

Finding

An out-of-range RGB component is reported through the logger in Java, to stderr in Go, and to stdout in C# and Swift, where it lands in the program's output.

Suggestion

Route the C# and Swift warnings to stderr or the port's logger.

Small shape and signature differences 9.0.0

Finding
  • Go CompositeTextLine.GetMinMaxY returns []float32; every other coordinate pair in Go is [2]float32.
  • Go PDF.AddObjects takes *[]*PDFobj and never uses the pointer; GetPageObjects and AddResourceObjects take the slice.
  • Go has AddBDC only in its four-argument form, so every caller passes "" for the language; the other ports have the three-argument form too.
  • Go Paragraph has no constructor from a TextLine; the others do.
  • Swift Title.setPrefix and TextLine.advance lack @discardableResult, so a plain call warns.
  • Swift PDF labels read(from:) and getPageObjects(from:) but not addObjects(_:) or addResourceObjects(_:).
  • Swift Page.addResource takes inout [PDFobj] for a core font and a plain array for an image or a font.
  • C# Page.setPenColor(int) and setBrushColor(int) repeat the array overload instead of calling it, and the saved graphics state stores pen and brush in the opposite order in Go and Swift from Java and C#: same bytes today, two things to keep in step.
Suggestion

Align each with the majority port; none changes output.

Tables, cells and forms 9.0.0

Finding
  • Go NewCell(font, text) is the only Cell constructor, and it always marks the cell as having text, so an empty string makes a cell one font height tall where Cell(font) in the other ports makes a cell of height zero.
  • Swift Cell.getProperties reports top and left whatever setBorder set; the four ports lay the same flags out four ways.
  • Go Cell.SetBorderColorRGB cannot clear the color; the other ports take null.
  • Swift Table.getWidth returns 0 for an empty table; the others fail on the first row.
  • RadioButton.setFontSize resizes the shared Font in every port; CheckBox stores its own size.
  • Swift Form copies the fields list; the other ports keep the caller's, so a field added later shows in three ports. Go Form.DrawOn has no nil page check where the others fail with a message.
  • Swift handles a nil page three ways: CalendarMonth skips the drawing, CheckBox and RadioButton unwrap, Form stops the program.
Suggestion

A Go constructor for a cell without text; one representation of the flags; a fontSize field on RadioButton; one nil page rule in Swift.

Images and groups 9.0.0

Finding
  • OptionalContentGroup.getComponents returns a copy in Swift and the live list elsewhere.
  • CoreFont(int) checks the number in no port; a bad value fails later in stringWidth.
Suggestion

Return the live list or a copy in all four, and reject a core font number outside the fourteen.

Stale lines and comments Tidy

Finding

Go rotateAroundCenter lives in the annotation file while the other ports keep it on Container; Go has an unused annotationType; Go doc comments still say Float.MIN_VALUE and carry Javadoc @param tags; the Go comment on rotate names the wrong center; DonutChart.java and Slice.java put the package line before the license.

Inconsistencies shared by all four ports

These are the same in every port, so they are design choices rather than drift, but two rules for one setting is one too many.

Two defaults for the accessibility text 9.0.0

Finding

Rect, TextLine and the annotations default altDescription and actualText to null; Line, Arc, Image, SVGImage, CheckBox and RadioButton default them to a single space.

Suggestion

One default. Null is the honest one: no description was given.

Color.transparent is honored by some text setters and not others 9.0.0

Finding

TextLine.setTextColor and setDecorationColor ignore Color.transparent; TextBlock.setTextColor and Cell.setTextColor turn it into white, because -1 shifts into 0xFFFFFF.

Suggestion

Treat Color.transparent the same everywhere, as the background and border setters already do.

setFont resets the fallback font in one class of three 9.0.0

Finding

TextBlock.setFont also sets the fallback font; TextLine.setFont and Cell.setFont keep the old fallback.

Suggestion

Pick one rule and apply it to the three.

Chart and BarChart disagree on zero and on their extras 9.0.0

Finding

Chart.setChartBorderWidth(0) draws the thinnest line; BarChart.setChartBorderWidth(0) hides the border. BarChart has setSubtitle, setGridLineColor and setAxisLineWidth; Chart has none and its grid is always black.

Suggestion

Give Chart the three setters and the same meaning of zero.

TextColumn.getHeight and getSize 10.0

Finding

TextColumn.getHeight returns the height that was set, where TextBlock.getHeight returns the height as drawn; the drawn height of a column comes from getSize, which returns a Dimension, a class that exists for this one method.

Suggestion

Part of the TextColumn into TextFrame fold below.

Getters that only TextLine has 10.0

Finding

TextLine has a getter for every setting. TextBlock lacks getters for line spacing, language, right to left, URI and highlight colors; TextColumn lacks them for line spacing, paragraph spacing and the line between paragraphs.

Suggestion

Add them when the text classes are next touched.

Names

The names that still say the wrong thing, or say one thing two ways.

Abbreviations 9.0.0

Finding

Chart.setDrawHGridLines, setDrawVGridLines, setHGridLineWidth, setVGridLineWidth, setHGridLineDashPattern and setVGridLineDashPattern are the only abbreviated setters in the library; BarChart spells out setGridLineWidth. Shape.H_DASH and V_DASH are the only abbreviated constants. Go qrcode.ErrorCorrectionLevelL repeats the type name where every other Go constant is package.Name, like alignment.Left.

Suggestion

setDrawHorizontalGridLines and the like, Shape.HORIZONTAL_DASH and VERTICAL_DASH, and a Go errorcorrectionlevel package with L, M, Q and H.

One name, two meanings 9.0.0

Finding

setLocation is the top left corner of every Drawable but the center of a DonutChart. Form.setFormWidth repeats the class name where every other class says setWidth. Path.setClosePath(boolean) reads as a command.

Suggestion

DonutChart.setLocation takes the top left corner of the outer circle, or the class documents its center loudly; Form.setWidth; Path.setClosed.

A field and its setter disagree 9.0.0

Finding

BaseAnnotation.setOpacity stores transparency, and writes it as /CA, which is opacity. Cell.setBorderColor stores strokeColor, CheckBox.setBorderColor stores boxColor, Form.setStrokeWidth stores lineWidth. TextLine.setDecorationColor stores lineColor. Chart.setHGridLineDashPattern stores hGridLinePattern. TextFrame.setParagraphGap stores paragraphLeading. CompositeTextLine.setSuperscriptFactor stores superscriptSizeFactor.

Suggestion

Rename the fields after the setters, in the four ports. Internal, so no caller changes.

Odd members 9.0.0

Finding
  • TextLine.getStringWidth(text) measures any text; that is Font.stringWidth, which exists.
  • TextLine.advance(leading) moves the line down and returns the new y; the name does not say it moves anything.
  • TextLine.getDestinationX and getDestinationY are the GoTo destination of the line; nothing in the name says so.
  • Arc.setSweepDegreesCW and setSweepDegreesCCW are two setters for one signed angle, in a library where every other angle is counterclockwise and positive.
  • Page.drawCircle takes a PathOperator while drawEllipse has a fillEllipse twin, and drawRectRoundCorners has neither an operator nor a fill twin.
  • Page.transform(float[]) takes the six values at Android Matrix indices, exposed as MSCALE_X and friends.
  • Table.getRowsRendered says "rendered" where the library says "drawn".
  • Go Font.GetAscentAt, GetDescentAt, GetBodyHeightAt and StringWidthFB use At and FB suffixes where the other Go overloads use a type suffix like RGB; Go XMarkCheckBox reads as a type.
  • The private key generator of Bookmark is next in Java, Next in C#, getNext in Go and goToNext in Swift; FileAttachment.setIconPushpin writes PushPin next to Paperclip.
Suggestion

Remove getStringWidth; moveDown(leading); getGoToDestinationX/Y; one setSweep(degrees), counterclockwise; fillRectRoundCorners or a PathOperator on all three; transform(a, b, c, d, e, f) in PDF order; getRowsDrawn.

Spacing has two names and two meanings 10.0

Finding

TextColumn.setParagraphSpacing is a multiple of the line height; TextFrame.setParagraphGap is points. That is the documented gap-versus-spacing rule, but it is the one place a reader meets both for the same thing.

Suggestion

Goes away with the fold below.

Permissions take an int in two ports and a type in two Document

Finding

Permissions.grant and setAccess take the UserAccess values as an int in Java and Swift and as a typed flags value in C# and Go, and the port note in the README says so. It is the last place a value has two types across the ports.

Fixed on 14 September

The bugs and the crash-class drift of this audit were fixed the same day, in the four ports, and are listed here so the page stays a record of what was found.

  • Java BarChart.barColor guards a negative index, so a named series with a color per bar draws its legend swatch; the bar chart tests now name such a series in all four ports.
  • Swift Page(pdf, pageObj) strips the comments before it reads the page size, as the other ports do.
  • Title.drawOn tests the prefix text in Java, C# and Go, as Swift did.
  • BaseAnnotation.rotate skips the vertices of a polygon that has none, in Java, C# and Swift.
  • Swift Image(pdf, path) throws a PDFjetError for a missing file; Image(objects, bytes) passes no alpha channel for a gray or 16-bit image; Image.drawOn no longer rounds its link rectangle.
  • Cell.setBorder in Java and C# masks the value with Border.ALL, so no stray bit reaches the underline and strikeout flags.
  • CompositeTextLine.getLocation returns a copy in Java and C#.
  • Go OptionalContentGroup.Clear allocates a new list, so a slice handed out earlier no longer sees later additions.
  • BigTable aligns a number with the same Table.isNumber test in the four ports, instead of each language's float parser; Go BigTable treats an empty delimiter as one field per line and reads lines longer than 64 KB, as Table does.
  • The font parser OTF and the PNG decoder PNGImage are internal in the four ports, as are the ICC profile bytes of Go and Swift and the Swift PDFobj.dict field. CheckBox.xMark stays public: Example_50 uses it to tick the boxes of an existing form, so it is a feature, not an internal, and the audit had it wrong.
  • The stale white fill color of the Go link annotations in Chart, TextBlock, Image, SVGImage, CheckBox, RadioButton and FileAttachment is gone.

Left for 10.0

Fold TextColumn into TextFrame once its CJK paragraphs, its line between paragraphs and its alignment move over. That also settles getSize, Dimension, the two paragraph spacings and the missing getters above. Touches Example_10, 29, 44, 49 and Cell.setTextColumn.

One table API. Table says setData and drawOn(pdf, pages, pageSize); BigTable says setTableData, setNumberOfColumns, setTextAlignment, complete and getPages. Give them the same names, or make streaming a mode of Table. Touches Example_43 and the seven Table examples.

Stamp keeps its own drawing API by decision: the form XObject is the point, and the API that fills it is a small cost.
